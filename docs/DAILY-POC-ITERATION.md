# Daily POC iteration and tuning guide

Tune the canonical manifest and reusable compiler, not generated artifacts and
not per-release scripts. Generated bytes are evidence: manual edits are drift.

## Daily refinement loop

1. **Plan:** freeze the source range and select only material user-visible
   changes. Define claims and non-claims at their current maturity.
2. **Do:** update one manifest, prepare into a new owned directory, and keep
   publication switches false.
3. **Check:** inspect the verdict, run deterministic verify and checksums, review
   narration against claim IDs, and record gate failure classes.
4. **Act:** correct the manifest or reusable compiler. Increment `N` for a new
   same-day candidate. Preserve blocked reports as negative evidence.

Do not add optional ceremony to L0/L1 source changes. Hard gates remain on
security/release claims, evidence integrity, unsafe content and public effects.

## Scene and narration gates

Each scene declares one stable ID, unique order, fixed logical duration,
purpose, narration, visuals, claim references and use-case references. The
compiler injects the exact claim statement and maturity into both narration and
storyboard facts. This prevents a locally validated claim from being presented
as merged or released.

Safe customization:

- change pacing, visuals or plain-language narration in `video.segments`;
- keep details such as IDs, versions and hashes in visuals;
- keep principles and user value in narration;
- bind new assertions to an existing or new stable claim ID and evidence;
- add accepted assets only with exact path, status and SHA-256.

Unsafe customization:

- editing generated narration or storyboard independently;
- using a wall-clock timestamp or nondeterministic scene order;
- adding release/production wording above evidence maturity;
- enabling render, upload or README changes as an editorial shortcut.

## Defaults and overrides

Manifest `controls` documents every default, permitted override and dependency.
Video render is the only local preparation override and remains closed behind
accepted assets plus an exact candidate-bound approval. Publication controls
have no override inside this pipeline. A later publication adapter must be a
separate Owner-authorized stage with its own audit record.

## First tuning metrics

Measure after each successful or blocked candidate:

- lead time from source freeze to candidate verdict;
- gate failure counts grouped by stable reason prefix;
- narration/storyboard correction count before acceptance;
- manual interventions and resume count;
- claim/evidence deviations;
- render/QC outcomes when rendering becomes locally eligible;
- reader comprehension and video readability feedback after separately
  authorized publication.

The deterministic `run-report.json` uses logical gate-step durations so fixed
inputs remain byte-identical. CI or the operator may observe wall time outside
the candidate package. Never inject live timings into checksum-bound outputs.

## Change and rollback discipline

Compiler/schema changes require a new schema/compiler version when they alter
meaning. Compatible wording or layout refinements keep v1 and add focused
fixtures. Update the change and decision logs, rerun the negative matrix, build
the example twice and compare every final byte. Roll back by reverting the
local pipeline commit; publication remains unaffected because no public effect
is part of this workflow.
